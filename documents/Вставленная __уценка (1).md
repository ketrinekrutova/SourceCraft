4Да. Я собрала это именно в формате, который уже можно использовать как **черновое техническое задание для backend-команды**.

Самое важное уточнение после повторной проверки документации: вам **не обязательно получать абсолютно всё через Public REST API**. В ТЗ разрешены активные интерфейсы SourceCraft — API/CLI, а сам SourceCraft официально позволяет клонировать репозитории через Git и получать RAW-файлы. Поэтому, например, историю коммитов и возраст `TODO` разумнее получать из Git, а не пытаться найти несуществующий REST-метод. SourceCraft подтверждает возможность клонирования публичных репозиториев и работу с их Git-историей. ([Vibecraft](https://vibe.sourcecraft.dev/portal/docs/en/sourcecraft/operations/repo-clone?utm_source=chatgpt.com "Cloning a repository SourceCraft | Overview"))

Обозначения в таблице: **✅** — данные напрямую подтверждены Public REST API; **⚙️** — SourceCraft отдаёт необходимые поля, а показатель рассчитывает ваш backend; **🔀** — реально получить из SourceCraft, но удобнее через файлы/RAW/Git, а не готовым REST-полем; **🔐** — должен идти из отдельного AppSec API, но точное название endpoint/поля ещё нужно подтвердить в Swagger.

Для Documentation REST API действительно отдаёт дерево файлов с `name`, `path`, `type`, поддерживает `recursive` и конкретную `revision`. Поэтому `README`, `LICENSE`, `CONTRIBUTING`, `CODEOWNERS` можно искать автоматически. ([SourceCraft](https://sourcecraft.dev/portal/docs/ru/api-ref/Repository/ListTree?utm_source=chatgpt.com "List Repository File Tree - Repository | Обзор")) Для содержимого файлов SourceCraft официально предоставляет RAW-файлы, а публичный репозиторий можно клонировать через Git. ([SourceCraft](https://sourcecraft.dev/portal/docs/ru/sourcecraft/operations/raw-content?utm_source=chatgpt.com "Скачать, скопировать или получить ссылку на исходный файл (RAW) в SourceCraft | Обзор"))

Для CI/CD картина особенно хорошая: API реально отдаёт `runs[].status`, а также `created_at`, `started_at`, `finished_at`, `updated_at`; статусы включают `success`, `failed`, `canceled`, `timeout` и другие. Поэтому success rate, failure rate, длительность и стабильность — **не предположение, а реально вычисляемые показатели**. ([SourceCraft](https://sourcecraft.dev/portal/docs/en/api-ref/CICD/ListRuns?utm_source=chatgpt.com "List CI Runs in Repository - CI/CD | Overview"))

Activity тоже хорошо обеспечена данными: Repository API отдаёт `last_updated` и счётчики PR/issues/branches/tags, отдельный endpoint отдаёт contributors, PR API — статусы и даты pull requests, Releases API — даты публикации releases. ([SourceCraft](https://sourcecraft.dev/portal/docs/en/api-ref/Repository/GetRepositoryByID?utm_source=chatgpt.com "Get Repository (By ID) - Repository | Overview")) Но полную commit-history я бы не пытался строить через REST: SourceCraft — Git-платформа, и для этой части логичнее клонировать репозиторий и использовать обычный Git. ([SourceCraft](https://sourcecraft.dev/portal/docs/en/sourcecraft/concepts/?utm_source=chatgpt.com "SourceCraft resource relationships"))

По Issues подтверждены `created_at`, `updated_at`, `completed_at`, priority, статус и связанные PR. Отдельный API комментариев возвращает `author` и `created_at`, поэтому даже **first response time действительно можно вычислить**, а не имитировать. ([SourceCraft](https://sourcecraft.dev/portal/docs/en/api-ref/Issues/ListRepositoryIssues?utm_source=chatgpt.com "List Repository Issues - Issues | Overview"))

С Security есть одно исключение. Само требование ТЗ однозначно: нужно брать реальные данные SourceCraft AppSec — SAST, SCA, secret scanning, severity и status исправления. Я вижу переданный вами отдельный Swagger AppSec, но через веб-чтение его OpenAPI-схема сейчас не раскрывает названия endpoint'ов и полей. Поэтому я намеренно **не придумала** `/vulnerabilities` или какое-нибудь `severity_level`. Перед программированием Security вашему разработчику нужно открыть Swagger и для этих пяти строк вписать точные `endpoint + field`.

### Как эти 36 показателей превращаются в 6 оценок

Схема должна быть одинаковой для всех категорий:

```text
SourceCraft
    ↓
сырой факт
    ↓
Indicator

passed / failed / no_data
или конкретное число
    ↓
нормализация 0–100
    ↓
Category Score
```

Например CI:

```text
50 последних CI runs

success = 44
failed  = 4
timeout = 2

↓

successRate = 88%
failureRate = 8%
timeoutRate = 4%

averageDuration = 7.3 min

↓

CI/CD Score = 86/100
```

То есть **SourceCraft никогда не сообщает вам ****`CI/CD Score = 86`**. SourceCraft отдаёт факты, а вашу воспроизводимую формулу пишете вы.

Для всей категории правило `no_data` тоже сохраняем. Если, например, из пяти Security-показателей удалось достоверно получить четыре, отсутствующий показатель **не получает 0** — он исключается из нормализации. А если не удалось получить вообще весь Security, категория получает:

```text
Security = {
    score: null,
    status: "no_data"
}
```

Это соответствует требованию ТЗ не путать плохой результат с отсутствием данных.

### Итоговая формула Repo Health

Я бы пока не менял предложенные в ТЗ веса:

```text
Documentation    15%
CI/CD            15%
Security         20%
Activity         15%
Issues           15%
Code Health      20%
--------------------
                 100%
```

Тогда при:

```text
Documentation = 90
CI/CD         = 82
Security      = 76
Activity      = 91
Issues        = 80
Code Health   = 70
```

получается:

```text
Health =
90 × 0.15 +
82 × 0.15 +
76 × 0.20 +
91 × 0.15 +
80 × 0.15 +
70 × 0.20

= 80.65
≈ 81 / 100
```

А если, например, Security = `no_data`, его 20% **не превращаются в ноль**. Оставшиеся веса суммарно равны 80, и результат пересчитывается относительно этих 80%.
