# CHECK.md — проверочный чек-лист

Тактический список: что именно проверить руками, в каком порядке, и что считать подтверждением/опровержением. Каждый пункт — из реального пробела, найденного при сверке `README.md` со спекой API (`documents/sourcecraft.swagger (1).json`, `documents/SCS_API_1.0.0_draft.pdf`), не гипотетический.

Пока не закрыт блок A — за B, C, D браться бессмысленно.

## A. Доступы

- [ ] Токен/ключ для **SourceCraft API** (`api.sourcecraft.tech`) получен.
- [ ] **OAuth-приложение Я ID** зарегистрировано: `client_id`, `client_secret`, `redirect_uri` под демо-домен.
- [ ] Доступ к **SCS Security API** получен: base URL, способ авторизации, права — драфт прямо говорит, что этого нет в спецификации, уточнять у администратора/владельца API отдельным сообщением организаторам.
- [ ] **SourceCraft CLI** установлен локально, пройден `cli-quickstart`.
- [ ] Сторонний хостинг под демо-стенд выбран и зарезервирован (VPS/Render/Fly.io).

## B. Проверка API вручную (сразу после получения токена, до написания кода)

### B1. Что реально анонимно, а что требует токен
В swagger ни у одной операции не указан `security` — неизвестно, что открыто, а что нет. Один и тот же запрос выполнить без токена и с токеном, зафиксировать код ответа:

| Эндпоинт | Без токена | С токеном |
|---|---|---|
| `GET /repos` (публичный каталог) | | |
| `GET /repos/{org_slug}/{repo_slug}/cicd/runs` | | |
| `GET /repos/{org_slug}/{repo_slug}/issues` | | |
| `GET /repos/{org_slug}/{repo_slug}/trees` | | |
| `GET /repos/{org_slug}/{repo_slug}/contributors` | | |
| `GET /repos/{org_slug}/{repo_slug}/releases` | | |
| `GET /repos/{org_slug}/{repo_slug}/rating` | | |

Взять для теста один и тот же публичный репозиторий из ответа `GET /repos`.

**Вывод записать в README (раздел 1.1):** нужен ли сервисный токен даже для публичного конвейера, или анонимных вызовов достаточно.

### B2. Список репозиториев пользователя (эндпоинта в спеке нет)
Гипотеза: личное пространство пользователя смоделировано как организация со `slug = username`.

- [ ] `GET /user` с токеном пользователя → получить `username`/`id`.
- [ ] `GET /orgs/{username}/repos` с тем же токеном → 200 со списком личных репозиториев, или 404?
- [ ] Если 404/пусто — попробовать `GET /orgs/id:{user_id}/repos` (на случай, если id профиля совпадает с id личной организации).
- [ ] Если ни один вариант не сработал — **гипотеза не подтвердилась**, значит эндпоинта для п. 5 ТЗ («Получить сведения о доступных пользователю репозиториях») в этой выгрузке действительно нет. Формулировать вопрос организаторам буквально так: *«Каким методом получить список репозиториев, доступных авторизованному пользователю, если в выгрузке `sourcecraft.swagger.json` такого эндпоинта нет?»*

**Вывод записать в README (раздел 1.1 и блокер 6.6).**

### B3. Маппинг `Repository.id` ↔ `gitRepo` (SCS API)
- [ ] Взять `id` репозитория из ответа основного SourceCraft API (`Repository.id`).
- [ ] Запросить `GET /v1/scans/latest?gitRepo=<этот id>` в SCS API.
- [ ] Результат 200 с `ScanSummaryDto` → маппинг подтверждён, `Repository.id` = `gitRepo`.
- [ ] Результат 404/ошибка → попробовать другие кандидаты: значение из `web_url`, отдельный `uuid`, если найдётся при появлении доступа к `getRepo` в SCS (в драфте этого метода нет — возможно, потребуется отдельный запрос организаторам).
- [ ] Зафиксировать рабочий вариант как единственный источник истины в коде (одна функция `resolve_git_repo_uuid(repo)`), не размазывать по местам использования.

### B4. Авторизация CLI для приватных репозиториев
- [ ] Клонировать публичный репозиторий через CLI без авторизации → ожидание: успех.
- [ ] Клонировать свой приватный репозиторий через CLI без спец-настроек → зафиксировать, что происходит (ошибка доступа/просит логин).
- [ ] Найти документированный способ передать токен/сессию пользователя в CLI из бэкенда (переменная окружения, конфиг-файл, флаг) — без этого приватный конвейер (раздел 1.1 README) не реализуем.

### B5. Крупный репозиторий (порог раздела 9.2 ТЗ)
Крупный = ≥10 000 файлов, или ≥20 000 коммитов, или ≥500 МБ рабочей копии.

- [ ] Найти такой репозиторий в `sourcecraft.dev/find/repositories`, либо подготовить свой и описать способ подготовки (раздел 9.2 ТЗ это прямо разрешает).
- [ ] Прогнать через полный конвейер сбора данных (API + CLI-обход файлов и истории).
- [ ] Замерить время и память на категориях, которые требуют полного обхода файлов/истории (Документация, Активность, Code health) — это единственные категории с риском не уложиться в разумное время на крупном репо.
- [ ] Если не укладывается — зафиксировать sampling-стратегию (уже упомянута как допущение в README, раздел 3.2, Code health) и то же самое, возможно, понадобится для Активности/Документации.

## C. Проверка методики Score на контрольных сценариях

Требование напрямую из критериев оценки (раздел 13.2 ТЗ, подкритерий 3 «Поведение методики на контрольных сценариях», до 2 баллов): методика должна быть прогнана на нескольких контрольных сценариях с ожидаемым и зафиксированным поведением. Заполнить перед финальной сдачей, репозитории — реальные из каталога SourceCraft, подобранные под профиль:

| # | Сценарий | Репозиторий (какой взять) | Ожидаемое поведение | Факт |
|---|---|---|---|---|
| 1 | Здоровый активный проект | | Score высокий по всем 6 категориям | |
| 2 | Критические уязвимости в зависимостях | | Security заметно падает, остальные категории не затронуты | |
| 3 | CI не настроен | | CI = 0 (не «нет данных»), но итоговый Score не обнуляется — категория весит 15% | |
| 4 | Давно не коммитили, но отличная документация | | Activity низкий, Documentation высокий, итог — средний, не «весь красный» | |
| 5 | Пустой/новый репозиторий (`is_empty=true`) | | Весь анализ = «нет данных», не 0 | |
| 6 | Много TODO/FIXME, но все свежие (<180 дней) | | density снижен, freshness высокий — категория не в нуле | |
| 7 | Ни одного issue за всю историю | | Issues = «нет данных» (не 0, не 100) | |
| 8 | Ни одного скана AppSec | | Security = «нет данных» | |

Если факт расходится с ожиданием — правим формулу (раздел 3.2 README), а не подгоняем сценарий.
