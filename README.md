# SourceCraft Repo Health

Веб-сервис, который регулярно анализирует открытые репозитории SourceCraft, считает **Repo Health Score (0-100)** по шести категориям, объясняет оценку и даёт приоритизированные рекомендации с подтверждающими фактами. Авторизованный через Я ID пользователь анализирует свои репозитории (в том числе приватные) с данными AppSec. Кейс №8 Yandex Cloud, хакатон «Лидеры цифровой трансформации 2026».

## О проекте

**Проблема.** Чтобы понять, в каком состоянии открытый проект (развивается ли он, стабилен ли CI, есть ли уязвимости, понятна ли документация), приходится вручную сопоставлять git-историю, README, пайплайны, issues и результаты сканирования безопасности. С ростом числа проектов на SourceCraft ручная оценка не масштабируется.

**Решение.** Сервис собирает эти сигналы через API и git SourceCraft, превращает их в понятную оценку с объяснением и конкретными шагами по улучшению.

**Для кого:** разработчики и мейнтейнеры, тимлиды и CTO, команды, выбирающие открытые компоненты, администраторы платформы SourceCraft.

### Возможности

- **Рейтинг открытых репозиториев.** Весь каталог SourceCraft (~28 тыс. репозиториев) с сортировкой по Score, лайкам и активности, фильтром по языку и постраничным выводом. Score - главный фактор рейтинга, лайки на оценку не влияют.
- **Оценка по шести категориям:** Security, Code health, Activity, Documentation, CI/CD, Issues. Формулы и веса открыты, расчёт воспроизводим.
- **Страница анализа.** Итоговый Score и вердикт, оценки категорий с раскрытием «как посчитано» и подтверждающими фактами (файлы, коммиты, прогоны CI, issues, уязвимости), сильные и слабые стороны, таблица вклада категорий в Score, изменение к прошлому анализу.
- **Рекомендации.** Проблема, почему это важно, факты, что сделать, приоритет и рассчитанный эффект на Score («+10 к Documentation, ≈ +4 к Repo Health Score»).
- **Честная обработка отсутствия данных.** «Нет данных» с причиной отличается от плохой оценки и не снижает Score.
- **Анализ своих репозиториев.** Вход через Я ID, подключение PAT SourceCraft, список доступных репозиториев (включая приватные), личный анализ с Security по данным AppSec. Личные результаты видны только владельцу и не попадают в публичный рейтинг.
- **Отчёты.** Выгрузка в PDF и Markdown.
- **Периодический пересчёт.** Ежесуточный обход каталога и пересчёт по расписанию, ручной повторный анализ, очередь задач с горизонтальным масштабированием воркеров.
- **Крупные репозитории** (≥10 000 файлов / ≥20 000 коммитов) анализируются без падений по времени и памяти.

### Стек

Backend - Python 3.11+, FastAPI, SQLAlchemy (async), APScheduler, httpx, git, fpdf2; БД - PostgreSQL (SQLite для локального запуска). Frontend - React 19, TypeScript, Vite, TanStack Query. Развёртывание - Docker Compose (Postgres, API, воркеры, nginx).

## Быстрый старт

### Docker (полный стенд, Postgres)

```bash
cp .env.example .env        # заполнить SOURCECRAFT_SERVICE_PAT, YA_ID_*, SECRET_KEY
docker compose up -d --build
# http://localhost:8080 - интерфейс, http://localhost:8080/api/docs - Swagger API
docker compose up -d --scale worker=3   # больше воркеров
```

### Локально (SQLite, одна команда на процесс)

Нужны Python 3.11+, Node 20+, git.

```bash
# бэкенд: API + воркер + планировщик в одном процессе
cd backend
python -m venv .venv && .venv/Scripts/activate        # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
cp ../.env.example .env    # для локального входа без Я ID: DEV_LOGIN_ENABLED=true, FRONTEND_URL=http://localhost:5173
uvicorn app.main:app --port 8000

# фронтенд (проксирует /api на :8000)
cd frontend && npm ci && npm run dev    # http://localhost:5173
```

Без `SOURCECRAFT_SERVICE_PAT` рейтинг всё равно наполняется **всеми открытыми репозиториями**: официальный API без токена отвечает 401, поэтому каталог берётся из открытой страницы sourcecraft.dev/find/repositories (см. «Источники данных»). Для анализа в этом режиме CI/CD и Issues будут «Нет данных», а Documentation, Activity и Code health считаются по git. При первом запуске с пустой базой обход каталога и постановка всех репозиториев в очередь происходят автоматически.

### Воспроизведение результатов без UI

```bash
cd backend
python -m app.cli analyze aladin/showcase-math-whiz   # анализ одного репозитория с выводом Score и рекомендаций
python -m app.cli sweep                              # то, что делает ночное расписание
python -m app.cli run-queue                          # выполнить очередь и выйти
python -m pytest -q                                  # 36 тестов: контрольные сценарии методики, API, доступ
```

## Архитектура

```
Браузер ── nginx (SPA + /api) ── FastAPI (API, Я ID OAuth, планировщик)
                                      │
                                 Postgres: repositories · analyses (история) · jobs (очередь) · users · user_repo_access
                                      │
                          воркеры ×N (python -m app.worker) ── SourceCraft API · AppSec API · git.sourcecraft.dev
```

| Слой | Код | Ответственность |
|---|---|---|
| Клиенты | `backend/app/clients/` | HTTP к API SourceCraft и AppSec (лимит частоты на хост, повторы на 429/5xx, классификация отказов); git: shallow-клон, чтение объектов, blame |
| Нормализаторы | `backend/app/normalizers/` | сырые ответы → `Facts` (чистые функции, покрыты тестами) |
| Скоринг | `backend/app/scoring/` | формулы категорий, агрегатор, рекомендации. Без I/O, результат воспроизводим на тех же фактах |
| Сервисы | `backend/app/services/` | сбор фактов (`collector`), выполнение задачи (`analysis`), очередь (`queue`), каталог (`repositories`) |
| Воркеры | `backend/app/workers/` | пул воркеров, ночной пересчёт каталога |
| API | `backend/app/routers/` | контракт - `backend/openapi.yaml`, живой Swagger - `/api/docs` |
| Фронтенд | `frontend/` | React + TypeScript + TanStack Query. Рейтинг, страница анализа, «Мои репозитории» |

Анализ всегда асинхронный: запуск возвращает `202` и `job_id`, фронтенд опрашивает статус раз в 2 с и сам обновляет страницу. Результат каждого анализа хранится целиком (`analyses.result_json`): страница и отчёты (PDF, Markdown) строятся из одной и той же записи, а история позволяет показать изменение Score к прошлому анализу.

## Источники данных и API

| Источник | Что берём | Для категорий |
|---|---|---|
| `api.sourcecraft.tech` ([документация API](https://api.sourcecraft.tech/docs/index.html)) | `GET /repos` (каталог), `/repos/{org}/{repo}` (метаданные, лайки, язык), `/cicd/runs`, `/issues` + `/issues/{slug}/comments`, `/pulls`, `/releases`, `/contributors`, `/trees` (запасной вариант при недоступности git), `/orgs/{org}/repos`, `/user` | CI/CD, Issues, Activity, Documentation, рейтинг, «Мои репозитории» |
| `sourcecraft.dev/gateway/root/api/listTopRepositories` (внутренний метод открытой страницы «Топ репозиториев») | каталог всех открытых репозиториев с лайками, языком и датой обновления - **только если PAT команды не задан** (проверено: 28 223 репозитория анонимно, ~100 с) | рейтинг |
| `git.sourcecraft.dev` (git-интерфейс платформы) | shallow-клон истории за 181 день без рабочей копии: дерево файлов, README, коммиты, TODO/FIXME, `git blame` | Documentation, Activity, Code health |
| `appsec.sourcecraft.tech` (спецификация - `/openapi` того же хоста) | `/v1/scans` (последний FINISHED), `/v1/defect-groups` с фильтрами по severity/status/type | Security |

Авторизация везде - `Authorization: Bearer <PAT>`. Публичный конвейер использует PAT команды (`SOURCECRAFT_SERVICE_PAT`), личный - PAT пользователя. Лимиты частоты от организаторов: AppSec - 100 rps, остальные хосты - 10 rps на каждый; по умолчанию используем 8 и 50 rps.

Проверено на реальных сервисах:
- API без токена отвечает 401 даже на каталог.
- Анонимный `git clone` публичных репозиториев работает.
- Partial clone (`--filter=blob:none`) git-сервер SourceCraft **не поддерживает**, поэтому объём ограничиваем глубиной истории.
- В AppSec поля `status`/`severity` групп дефектов - числа без таблицы соответствия. Поэтому количество по критичности берём из `totalSize` запросов с фильтрами по строковым enum (`severity=CRITICAL&status=OPEN…`).

## Методика Repo Health Score

**Итог:** `Score = Σ(score_k × w_k) / Σ w_k` по категориям со статусом OK, с округлением до целого. Веса методики: Security 20, Code health 20, Activity 15, Documentation 15, CI/CD 15, Issues 15. Категории «Нет данных» исключаются, остальные веса нормируются. Страница и отчёт показывают исходный вес, фактический вес и вклад каждой категории, а также «полноту данных» - долю веса, по которой есть данные.

Вердикт: ≥80 «Отличное состояние», 60–79 «Хорошее, есть точки роста», 40–59 «Требует внимания», <40 «Критическое».

Если внутри категории показатель не удалось измерить (например, нет ни одной закрытой задачи), он исключается с перенормировкой внутри категории - то же правило, что и между категориями.

### Метрики по категориям

**Security (20%)** - открытые группы дефектов AppSec (статусы OPEN, TRIAGE_IN_PROGRESS, TRIAGED_TP, FIX_IN_PROGRESS) последнего завершённого скана:
`score = max(0, 100 − (20·CRITICAL + 10·HIGH + min(30, 4·MEDIUM) + min(10, LOW)))`.
Потолки для средних и низких нужны, чтобы сотня мелких находок не перевесила одну критическую. В детали выводятся разбивка SAST/SCA/SECRETS и число исправленных (RESOLVED_FIXED/AUTOFIXED).

**CI/CD (15%)** - последние ≤50 прогонов; в знаменатель идут только success/failed/timeout:
`60·success_rate + 20·(1 − max(0, rate(прогоны 11–50) − rate(последние 10))) + 20·clamp(1 − дней_с_последнего_прогона/90)`.
Прогонов нет → 0 («CI не используется»). В детали выводятся медианная длительность и доля падений отдельно на push и на PR.

**Documentation (15%)** - чек-лист: README 20, инструкция установки/запуска в README 8, сборка/тесты в README 7, LICENSE 20, CONTRIBUTING 10, CODEOWNERS 10, манифест сборки 10, тесты 5, структура каталогов 10. Секции README ищутся эвристикой по заголовкам и командам.

**Activity (15%)** - непустые не-merge коммиты:
`35·clamp(1 − дней_с_коммита/180) + 25·clamp(коммитов_в_неделю_90д/5) + 15·clamp(авторов_90д/3) + 20·clamp(merged_MR_90д/10) + релиз (5 если <90 дн., 2 если <180, иначе 0)`.
Время мержа в API нет, поэтому для MR в статусе merged используется `updated_at`. В детали выводятся тренд к предыдущим 90 дням, доля топ-автора (bus factor), число контрибьюторов (`/contributors`), открытые MR.

**Issues (15%)** - `40·(1 − зависшие/открытые) + 25·clamp(1 − ср_время_первого_ответа/14) + 15·clamp(1 − медиана_закрытия/30) + 20·(1 − clamp(доля_critical_blocker/0.3))`.
«Зависшая» - открыта и не обновлялась больше 30 дней. Первый ответ - первый комментарий не автора; считается по выборке из 30 последних задач, чтобы не расходовать квоту API.

**Code health (20%)** - TODO/FIXME/HACK/XXX в исходниках (без vendor, node_modules, сгенерированного и собранного кода):
`60·(1 − clamp(маркеров_на_1000_строк/10)) + 40·(1 − старые/все)`.
«Старый» - строка старше 180 дней по `git blame`. Для файлов сверх лимита blame берётся дата последнего изменения файла. Нормировка на KLOC нужна, чтобы большой проект не наказывался сильнее маленького. В детали выводятся файлы длиннее 1000 строк.

### Устойчивость и контрольные сценарии

- Потолки `clamp` не дают накрутить Score активностью: 500 коммитов в неделю дают столько же, сколько 5. Пустые коммиты не считаются вовсе.
- Лайки не входят в Score; при любой сортировке рейтинга вторичный ключ - Score.
- Один второстепенный показатель ограничен своей долей: например, релизы весят 5% внутри Activity, то есть 0,75% итога.

Контрольные сценарии (`backend/tests/test_scoring_scenarios.py`, запускаются в CI-тестах):

| Сценарий | Ожидание | Проверка |
|---|---|---|
| Здоровый активный проект | все категории ≥70, итог ≥90 | ✔ |
| 2 критические уязвимости | Security ≤61, итог падает ≥5 пунктов | ✔ |
| 200 низких vs 1 критическая | 200 низких лучше одной критической | ✔ |
| CI нет | CI = 0 (не «нет данных»), итог не обнуляется | ✔ |
| CI падает в 50% / деградирует | заметно ниже зелёного / ниже восстановившегося | ✔ |
| Давно не коммитили, отличная документация | Activity <30, Documentation ≥65, итог средний | ✔ |
| Пустой репозиторий | «Нет данных», не 0 | ✔ |
| Много свежих TODO | категория не в нуле; старые TODO хуже свежих | ✔ |
| Нет issues / нет доступа | «Нет данных» | ✔ |
| Нет сканов AppSec | «Нет данных», итог не падает | ✔ |
| Спам пустыми коммитами | Activity не растёт | ✔ |
| Исправление по рекомендации | рассчитанный прирост Score > 0 | ✔ |

## Правила обработки отсутствующих данных

«Нет данных» ставится, **только если источник не ответил** (нет прав, 401/403/404, таймаут, сбой) или данных принципиально нет. Если источник ответил нулём, это вычисленный результат:

| Ситуация | Статус |
|---|---|
| Прогонов CI нет, или API недоступен и в дереве нет `.sourcecraft/ci.yaml` | 0 - CI не настроен |
| CI-конфиг есть, но статусы прогонов недоступны (чужой репозиторий) | Нет данных |
| AppSec недоступен / сканов нет / публичный режим | Нет данных |
| Issues недоступны или в трекере нет ни одной задачи (задачи могут вестись вне платформы) | Нет данных |
| Пустой репозиторий / нет исходников (для Code health) / сбой клонирования | Нет данных |

Каждая категория «Нет данных» показывает причину в интерфейсе и отчёте и визуально отличается от плохой оценки (штриховка вместо полосы). Если источник частично недоступен из-за ошибки, анализ получает статус `PARTIAL` со списком отказавших источников. Если анализ упал целиком, **предыдущий результат сохраняется**, а в интерфейсе появляется пометка «анализ не обновлён».

## Алгоритм рекомендаций

Рекомендации строятся детерминированными правилами (`backend/app/scoring/recommendations.py`, без LLM). Каждое правило:

1. срабатывает по порогу на фактах: критические уязвимости и секреты; >20% падений CI (≥50% - высокий приоритет); нет CI; нет README/лицензии/инструкции запуска; >180 дней без коммитов; bus factor = 1; зависших задач ≥20%; critical/blocker; TODO старше 6 месяцев; плотность >5 маркеров на KLOC;
2. содержит проблему, почему это важно, факты, действие и ссылки на подтверждения (файл:строка, прогон CI, группа дефектов, issue, коммит);
3. описывает «исправленное» состояние фактов. Движок **пересчитывает категорию и итоговый Score той же формулой**, поэтому эффект вида «+10 к Documentation, ≈ +4 к Repo Health Score» - это разница двух расчётов, а не оценка на глаз.

Приоритет задаётся риском (безопасность и сломанный CI выше гигиены репозитория), внутри приоритета рекомендации сортируются по рассчитанному приросту Score.

## Авторизация и доступ к закрытым данным

- Вход - OAuth 2.0 через Я ID (`/api/v1/auth/yandex/login`), сессия хранится в подписанной httpOnly-cookie. OAuth-токен Яндекса не сохраняется.
- Доступ к данным SourceCraft пользователь даёт своим PAT (так предложили организаторы). Токен проверяется запросом `GET /user` и хранится только зашифрованным (Fernet).
- «Мои репозитории» = личное пространство (org = username) + организации, указанные пользователем + любой репозиторий по ссылке. Эндпоинта «все репозитории пользователя» в выгрузке API нет.
- Личный анализ выполняется **только с PAT пользователя**, включая AppSec. Сервисный токен для чужих данных не используется.
- Закрытые данные отдаются только пользователю с подтверждённым доступом (`user_repo_access`). Подтверждение старше часа перепроверяется у SourceCraft; при отзыве доступа закрывается и уже посчитанный отчёт. Удаление PAT снимает все подтверждения.
- Приватные репозитории и личные анализы **никогда не попадают в публичный рейтинг**. Публичный рейтинг считается только по открытым данным, без AppSec: так единая методика одинаково применяется ко всем репозиториям.

## Периодический пересчёт и масштабирование

- Расписание `SCHEDULE_CRON` (по умолчанию `0 3 * * *` UTC, раз в сутки): обход всего каталога `GET /repos`, затем постановка в очередь репозиториев, чей публичный анализ старше `RECALC_INTERVAL_HOURS` (24 ч); сначала идут ни разу не анализированные. Обоснование: код публичных проектов меняется медленно, а полный обход каталога при лимите 10 rps занимает часы, так что чаще пересчитывать бессмысленно. Ручные запуски пользователей имеют более высокий приоритет и обгоняют ночной пересчёт.
- Очередь хранится в БД. Воркеры (`python -m app.worker`) забирают задачи через `SELECT … FOR UPDATE SKIP LOCKED`, поэтому процессов можно запускать сколько угодно (`docker compose up --scale worker=N`). Задачи упавшего воркера по heartbeat возвращаются в очередь (до 3 попыток).
- Запуски идемпотентны: пока анализ репозитория в очереди или выполняется, повторный запуск возвращает ту же задачу.
- Рейтинг строится одним индексированным запросом по денормализованному последнему публичному Score.
- Лимит частоты действует на процесс. При N процессах задайте `SOURCECRAFT_API_RPS ≈ 10/N`.
- Для демонстрации: «Повторный анализ» на странице репозитория меняет дату, статус и результат и показывает изменение к прошлому анализу. Конфигурация расписания - `backend/app/workers/scheduler.py` и `.env`.

## Крупные репозитории

Порог ТЗ: ≥10 000 файлов, ≥20 000 коммитов или ≥500 МБ.

- `git clone --shallow-since=<181 день> --no-checkout --single-branch`: история нужна только за окно метрик. Строки, которые blame относит к границе shallow-истории, заведомо старше 180 дней.
- Рабочая копия не создаётся: файлы читаются потоком через `git cat-file --batch`, память не зависит от размера репозитория.
- Бюджет сканирования: до 20 000 исходных файлов и 200 МБ, файлы до 1 МБ. Если лимит превышен, берётся детерминированная выборка (сортировка по хэшу пути): Score воспроизводим, а в интерфейсе видна пометка «по выборке».
- `git blame` запускается только для 40 файлов с наибольшим числом маркеров, для остальных берётся дата изменения файла.
- Таймаут клона - `CLONE_TIMEOUT_S` (15 мин). Временный каталог удаляется в `finally` сразу после разбора.

Способ подготовки крупного репозитория: `python scripts/make_large_repo.py ./large-repo` создаёт 12 001 файл и 20 500 коммитов за ~7 с, после чего его можно запушить в SourceCraft. Замер на нём: клон 3 с, анализ кода и истории 12 с, пик памяти Python 9 МБ.

## Ограничения

- **Security в публичном рейтинге не учитывается:** AppSec чужих репозиториев недоступен, собственное сканирование запрещено ТЗ. Полная оценка с Security - только в личном анализе.
- **CI/CD и Issues** для чужих публичных репозиториев зависят от прав сервисного токена; где их нет - «Нет данных».
- Время мержа MR приближается по `updated_at` (поля `merged_at` в API нет).
- Шаблоны веб-ссылок на файлы, issues и прогоны (`backend/app/normalizers/common.py`) проверить автоматически нельзя: SPA отвечает 200 на любой путь.
- «Мои репозитории» показывают личное пространство и указанные организации. Остальные доступные репозитории добавляются по ссылке, права проверяет SourceCraft.
- Отчёт выгружается в Markdown и PDF.
- Каталог без PAT берётся через внутренний недокументированный метод веб-интерфейса SourceCraft (`backend/app/clients/sourcecraft_web.py`); при изменении его формата правится один модуль, а с PAT используется официальный `GET /repos`.
- Первичный расчёт всего каталога (~28 тыс. репозиториев) занимает часы: до его окончания нерассчитанные репозитории стоят в конце рейтинга с пометкой «ожидает анализа».
- Схема БД создаётся через `create_all` при старте. Миграции (Alembic) понадобятся при изменении схемы на рабочем стенде.

## Часть со звёздочкой и AI

Полноценно звёздочка не делалась, но есть заделы: история Score по репозиторию (`/repositories/{id}/history`, изменение к прошлому анализу на странице), доля топ-автора (bus factor) и рекомендация при bus factor = 1, защита формулы от пустых коммитов и накрутки активности.

**Внешние сервисы и AI:** используются только SourceCraft API, AppSec API, git SourceCraft и Я ID. LLM и сторонние AI-сервисы не используются. Исходный код репозиториев никуда не передаётся и не хранится после анализа.
