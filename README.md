# SourceCraft Repo Health

Веб-сервис, который считает **Repo Health Score (0–100)** для открытых репозиториев SourceCraft, объясняет оценку и даёт приоритизированные рекомендации по улучшению. Кейс хакатона Yandex Cloud «Лидеры цифровой трансформации», 2026.

Полное ТЗ: `documents/task.pdf`. Этот README — рабочий план реализации, а не пересказ ТЗ.

## Договорённости по объёму

- В работу берём **только обязательную часть ТЗ** (раздел 3–6). Часть со звёздочкой (раздел 7) **не делаем** — даёт максимум 5 бонусных баллов из 105 и не компенсирует пробелы в обязательной части (п. 13.6). Если после сдачи обязательной части останется время — возвращаемся к этому вопросу отдельно.
- Стек: **Python (FastAPI) + React**.
- Команда: 2+ человека — работу можно параллелить (бэкенд/сбор данных, скоринг, фронтенд).
- Демо-стенд: сторонний хостинг (VPS / Render / Fly.io и т.п.), не Yandex Cloud.
- Доступов пока нет ни к одному внешнему ресурсу (см. «Блокеры» — это первое, что нужно закрыть).

## 1. Источники данных

Готовых выгрузок нет, всё собираем через живые интерфейсы. Три независимых источника с разной авторизацией:

| Источник | Что даёт | Файл-справка | Статус доступа |
|---|---|---|---|
| **SourceCraft API** (`api.sourcecraft.tech`) | repos, issues, pulls, cicd/runs, contributors, releases, rating (лайки), branches, tags, trees | `documents/sourcecraft.swagger (1).json` (167 эндпоинтов), `documents/GetAllPublicRepos.txt` (схема `GET /repos`) | нет токена |
| **SourceCraft CLI** | клонирование/чтение содержимого репозитория для анализа файлов (README, LICENSE, CONTRIBUTING, структура, TODO/FIXME в коде) | `sourcecraft.dev/.../cli-quickstart` | не установлен/не настроен |
| **SourceCraft Security API (SCS)** | результаты SAST/SCA/secret scanning: `/v1/scans`, `/v1/defect-groups`, `/v1/findings`, генерация отчёта | `documents/SCS_API_1.0.0_draft.pdf` | нет доступа, base URL и способ авторизации **не описаны в спецификации** — уточнить у организаторов |

Важное ограничение по SCS API (из драфта, дословно неочевидные места):
- Все методы требуют `gitRepo` (внутренний ID или UUID) — обычного репозитория по `org/repo` там нет; UUID репозитория для SCS придётся получать из основного SourceCraft API и матчить руками (маппинг репозиториев между двумя API — отдельная задача).
- В выгрузке **нет методов запуска сканирования** — сервис только читает результаты уже прошедших сканов. Если у репозитория сканов не было — это легитимный кейс «нет данных», а не ошибка интеграции.
- Списки пагинированы (`pageSize` 1–250, по умолчанию 50), нужно учитывать при обходе большого количества репозиториев.
- Security-данные нельзя подменять собственным сканированием (прямое ограничение ТЗ, раздел 3.1).

## 2. Архитектура (верхний уровень)

```
┌─────────────┐     ┌──────────────────┐     ┌─────────────────────┐
│   React SPA │◄───►│   FastAPI backend │◄───►│  Postgres            │
│ (rating,    │     │  - REST API        │     │  - repos             │
│  analysis,  │     │  - Я ID OAuth      │     │  - scores по версиям │
│  own-repo)  │     │  - report export   │     │  - findings/факты    │
└─────────────┘     └────────┬──────────┘     │  - job runs          │
                              │                └─────────────────────┘
                     ┌────────▼──────────┐
                     │  Scheduler/worker  │
                     │  (Celery + Redis   │
                     │   или APScheduler) │
                     │  - сбор данных     │
                     │  - расчёт Score    │
                     └────────┬──────────┘
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
      SourceCraft API   SourceCraft CLI    SCS Security API
```

Ключевые архитектурные решения и почему:
- **Расчёт Score асинхронный, не в request-цикле.** Анализ репозитория (особенно крупного, см. п. 4) может занимать минуты — обязателен воркер с очередью, а не синхронный HTTP-хендлер.
- **Хранить факты, а не только итоговый Score.** Каждая рекомендация должна ссылаться на факт (файл/pipeline/vulnerability/commit/issue/MR) — значит в БД нужна таблица «сырых» находок по категориям, из которых Score и рекомендации выводятся детерминированно и воспроизводимо.
- **Версионировать расчёты по времени.** Даже без «истории Score» (это звёздочка) нужно поле `analyzed_at` + возможность различить «текущий» и «предыдущий» расчёт — это явно требуется для демонстрации повторного анализа (раздел 6).
- **Не хранить исходный код дольше необходимого** (ограничение 2 из раздела 11). CLI используется потоково/во временной директории с последующей очисткой — не как постоянное хранилище.

## 3. Repo Health Score — методология

Нужно спроектировать и задокументировать собственную формулу. Ориентир весов из ТЗ (можно менять, но обосновать):

| Категория | Вес (ориентир) |
|---|---|
| Security | 20% |
| Активность проекта | 15% |
| Документация и лучшие практики | 15% |
| CI/CD | 15% |
| Issues | 15% |
| Code health (техдолг) | 20% |

Обязательные свойства методики (это прямо часть критериев оценки, до 10 баллов из 30, раздел 13.2):

1. **Все 6 категорий учтены**, либо явно обоснованное исключение/объединение с компенсацией — иначе 0 баллов подкритерия.
2. **Формула, веса и нормализация воспроизводимы** — не «чёрный ящик», должно быть описано так, что сторонний человек посчитает тот же Score по тем же исходным данным.
3. **Статус «Нет данных» ≠ плохая оценка.** Категория без данных не должна тянуть Score вниз автоматически — нужен явный механизм (например: категория исключается из взвешенной суммы и веса перераспределяются, а не подставляется 0).
4. **Устойчивость к перекосам.** Один второстепенный показатель не должен решать итог; методика не должна поддаваться дешёвому «накручиванию» (пустые коммиты, фиктивная активность и т.п. — это не подменяет обязательную устойчивость формулы, отдельно от звёздочки «защита от накрутки»).
5. **Проверяется на контрольных сценариях** — до сдачи нужно прогнать методику на 3–5 репозиториях с заведомо разным профилем (много уязвимостей / нет CI / отличная документация, но давно не коммитили / и т.д.) и показать, что Score логично реагирует.

Практический план реализации: каждая категория — отдельная чистая функция `raw metrics → (score 0-100, confidence/has_data, explanation)`. Итоговый Score — взвешенная сумма только категорий с данными, веса нормализуются на сумму весов доступных категорий.

## 4. Функциональный объём (обязательная часть)

### 4.1 Публичный рейтинг
- Список открытых репозиториев SourceCraft, отсортированный по Repo Health Score.
- Колонки: место, название, ссылка, Score, лайки, язык, дата последней активности.
- Фильтр по языку; сортировка по Score / лайкам / активности.
- Переход из строки рейтинга на страницу анализа.
- Явный принцип: Score — главный сортировочный фактор, лайки не должны его перекрывать по умолчанию.
- **Приоритет охвата**: цель — покрыть все открытые репозитории SourceCraft, а не фиксированную демо-выборку (это отдельно оценивается).

### 4.2 Страница анализа репозитория
Обязательные блоки (раздел 3.4 ТЗ):
- название + ссылка на репозиторий, дата последнего анализа;
- итоговый Score + разбивка по 6 категориям;
- сильные/слабые стороны;
- объяснение расчёта (какие метрики → какой вклад);
- список приоритизированных рекомендаций, каждая: проблема → почему важна → на каких фактах → что делать → приоритет → ожидаемый эффект на Score;
- явное отображение «нет данных» там, где категория не посчитана;
- кнопка выгрузки отчёта (Markdown или PDF — делаем один формат, выбор ниже).

### 4.3 Авторизация и анализ своего репозитория
- OAuth через Я ID.
- После входа — список репозиториев, доступных пользователю в SourceCraft (включая приватные).
- Запуск анализа по требованию, тот же движок скоринга, что и для публичных репо.
- **Контроль доступа**: приватные данные показываются только владельцу/участнику с правами — это отдельно проверяется на демонстрации, ошибиться здесь дорого по описанию ТЗ.

### 4.4 Периодический пересчёт
- Планировщик, который регулярно (периодичность — наш выбор, зафиксировать и обосновать, например раз в 24 часа для публичных репо) пересчитывает Score для открытых репозиториев.
- Хранит время и статус последнего анализа per-repo.
- Устойчив к временной недоступности источника (SCS/SourceCraft API упал → предыдущий Score сохраняется, репозиторий помечается «анализ не обновлён», а не падает целиком).
- На демо достаточно: ручной первичный запуск → ручной повторный запуск → показать, что статус/время/результат обновились + показать конфиг/код, которым включается расписание. Дожидаться реального срабатывания по крону на питче не нужно.

### 4.5 Выгрузка отчёта
Выбрать один формат — **Markdown** дешевле в реализации (шаблонизация из тех же данных, что рендерятся на странице), PDF требует рендер-пайплайн (например, WeasyPrint/Playwright). Рекомендация: делать Markdown как основной, PDF — если останется время, конвертацией из того же Markdown.

## 5. Нефункциональные требования

- **Крупные репозитории**: считается крупным репозиторий с ≥10 000 файлов, ≥20 000 коммитов или ≥500 МБ рабочей копии. Нужно либо найти такой публичный репозиторий в каталоге SourceCraft, либо подготовить свой и задокументировать способ подготовки. Анализ такого репо не должен падать по таймауту/памяти — учитывать при выборе способа обхода дерева файлов и git-истории (стриминг, а не полная загрузка в память).
- **Масштабирование**: обосновать подход (даже если на демо-стенде это один воркер) — например, воркер-пул с очередью задач по repo_id, идемпотентный пересчёт, что позволяет добавить инстансы горизонтально.
- **Приватность/лицензии**: не хранить исходный код дольше анализа; при использовании внешних LLM/сервисов — учитывать лицензию репозитория (если решим использовать AI — сейчас не планируем, см. «Договорённости»).
- **Обработка ошибок источников**: любой недоступный источник данных — это состояние "нет данных" для соответствующей категории/метрики, а не 500-я ошибка всей страницы анализа.

## 6. Блокеры — закрыть в первую очередь

Ничего из внешних доступов пока не получено. Это стартовая точка, без неё нельзя проверить ни одну гипотезу по данным:

1. Токен/ключ для **SourceCraft API** (`api.sourcecraft.tech`).
2. Регистрация **OAuth-приложения Я ID** (client_id/secret, redirect URI под демо-домен).
3. Доступ к **SCS Security API**: base URL, способ аутентификации, права — в самом драфте явно сказано, что это не описано и «нужно уточнить у администратора/владельца API». Без этого весь блок Security (20% веса методики, обязательная категория) не реализуем — это риск №1 проекта, эскалировать организаторам сразу.
4. Установка и проверка **SourceCraft CLI** локально.
5. Выбор и резервирование стороннего хостинга под демо-стенд.

## 9. Как нас будут оценивать

100 базовых баллов + до 5 бонусных (не в scope сейчас):

| Критерий | Баллы |
|---|---|
| Рабочий продукт | 35 |
| Качество метрик и аналитики (из них методология Score — 10, аналитика/рекомендации — 20) | 30 |
| UX дашборда и рейтинга | 15 |
| Качество демонстрации | 15 |
| Качество презентации | 5 |

Из этого явно следует приоритет разработки: **работающий сквозной сценарий на реальных данных важнее количества фич**. Лучше меньше метрик, но воспроизводимых и объяснимых, чем много метрик без обоснования (это прямо частично оцениваемый критерий, не общие слова).
